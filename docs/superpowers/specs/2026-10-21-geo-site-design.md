## 1. 意图

澳觅（澳门本地生活平台：外卖 / 超市生鲜 / 团购优惠 / 景点门票）想知道：内地游客和本地用户问豆包"澳门点外卖用什么 App"这类问题时，豆包有没有提到澳觅、排第几、引用了哪些网站；再根据这些数据决定去哪些平台发文章、写什么样的文章，并追踪文章有没有被豆包引用。

市面上的 Answerbit（腾讯企点营销云）做的就是这件事，但要收费，所以自建一个只给内部用的版本【用户定】。界面和功能结构参考 Answerbit【用户定】。第一期只做豆包【用户定】。

## 2. 目标 / 非目标 / 反目标

### 目标（MVP）
1. 每天 10:00（北京时间）【用户改，2026-10-22；原为 06:00】自动用豆包 API 跑 v3 冻结的 15 道题，**只跑一种联网渠道**【用户定，2026-10-21】，用 `api-custom`（豆包搜索 Custom 版）【用户定，2026-10-21；理由和切换条件见 §4.3】。渠道在设置里可以切换，换了以后看板要按渠道分开显示，不和之前的数据接成一条线。同一天另外用低频网页采集跑一遍这 15 题（`channel=web`），作为"更接近真实用户"的数据【用户定】。
2. 看板显示提及率、首位率、提及份额（澳觅 / mFood / 闪蜂），每个数字可以点进去看到原始回答和信源。
3. 信源分析：按平台统计被引用次数，重点看 7 个可发布平台。
4. 优化建议：找出短板题，结合信源给出"该去哪个平台发"的排序。
5. GEO 文章：基于知识库（RAG）生成文章，每条关于澳觅的事实挂出处，人工审核后手动发布，回填链接，自动追踪这个链接什么时候出现在豆包的信源里。
6. 知识库：上传 PDF（文字版，单个 100MB+）【用户定】，切块入向量库。
7. App 手测录入：每 1–2 周人工在豆包 App 上测一轮，录入后与 API 数据分开展示，用于校准。
8. 部署在公司 Linux 服务器，Docker，公网访问【用户定】，必须登录。

### 反目标（技术上能跑，但出现以下任何一条都算做砸了）
1. **看板上出现不是真实采集得到的数字。** 同事之前用的 WorkBuddy 工作台，提及率是 LLM 按规则模拟出来的，这正是要避免的。任何数字都要能追溯到具体的 run 和原始响应。
2. **API 数据和 App 数据被合并计算，或者被说成是"豆包 App 的表现"。**
3. **包含没有出处的澳觅事实的文章被标记为"可发布"。**
4. **数字不带样本量。** 看板正常展示每日数据【用户定】，但每个比率都要同时显示分子和分母（例如"8/10"），让看的人知道一道题的变化就会带来 10 个百分点的波动。
5. **漏跑的那天用前一天的数顶上。**
6. **为了让指标好看去改口径。** 口径改动只能升 schema 版本。
7. **网页采集为了"跑通"去绕过豆包的防护**，比如破解验证码、伪造指纹、轮换 IP、多账号轮换、随机化行为来躲检测。一旦出现这些做法，性质就从违反用户协议升级为协议 §5.1.2 所说的危害网络安全行为。

### 成功标准【我定，用户未回答，待确认】
上线后一个月内：
- 连续 14 天自动采集成功率 ≥ 13/14；漏跑的天在看板上显示为缺失。

## 4. 已决定的"怎么做"

### 4.1 部署架构
- 公司 Linux 服务器，Docker Compose，公网访问【用户定】。
- 容器【我定】：
  - `web`：后端 API + 前端静态文件
  - `worker`：定时任务（每天采集）+ 后台任务（PDF 入库、文章生成）
  - `mysql`：业务数据库【用户定：MySQL】，新起一个容器【我定，若公司要求复用现有实例再改】
  - ~~`qdrant`：向量库【我定，用户授权"听你的建议"】。选它是因为检索时能按元数据过滤（只搜现行版本的文档），MySQL 社区版又算不了向量距离~~ **2026-10-23 取消，不单独起向量库容器**，向量存 MySQL、在应用里算距离，见 §4.8【用户定】
  - 反向代理（nginx 或 Caddy）负责 HTTPS，并放开大文件上传
- 技术栈【我定】：后端 Python（FastAPI），因为现有采集脚本 `collect/doubao_api.py` 是 Python；前端 React + Ant Design + ECharts。
- 写文章和 embedding 都用火山方舟的模型，复用同一个 `ARK_API_KEY`【我定】。embedding 用哪个模型 ID，**由 builder 查方舟官方文档确定**，不要凭记忆写。

### 4.2 安全
- 必须登录，没有公开页面。账号由管理员创建，所有人权限相同【我定】。密码哈希存储，登录接口限流。
- `ARK_API_KEY` 只放服务器上的环境变量或 `.env`，不进数据库、不进代码仓库、不在页面上显示。之前在对话里出现过的 Key 要在上线前轮换。
- 公网暴露的风险：需要用户提供域名和 HTTPS 证书方案【待用户提供】。
- **服务器在内地，公司有域名**【用户定】：用这个域名下的一个子域名（例如 `geo.<公司域名>`）。上线前要请运维确认两件事：这个域名已经做过 ICP 备案；备案的接入商和服务器所在的云厂商是同一家。如果不是同一家，要先做「新增接入」。

### 4.3 数据来源与采集
- 复用 `collect/doubao_api.py` 里的 `build_body` / `parse_response` / `search_queries`，改成写 MySQL（原始响应 JSON 照旧落盘或存库）。
- **渠道选择**【用户定，2026-10-21；我推荐时的把握约 55%】：用 `api-custom`。依据是 trial 数据（每题只跑了 1 次）：
  - 两种渠道的信源域名重合度很低：逐题 Jaccard 平均 0.23，有 3 道题完全没有重合，说明它们背后是两套不同的搜索；
  - 原始响应的 `usage.tool_usage_details` 里，custom 标为 `doubao`，plugin 标为 `search_engine`，所以推测 custom 用的是豆包自己的搜索，更可能接近豆包产品，**这一点没有核实**；
  - 计费的搜索次数，custom 是 42 次/15 题，plugin 是 83 次/15 题；
  - 代价：custom 会忽略 `user_location`，每次返回的信源也少一些（平均 4.6 条，plugin 是 6.4 条）。
  - **切换条件**：网页采集（§4.3.1）攒满 14 天后，比较两种渠道和 web 在"是否提及澳觅"上的逐题一致率。为此，网页采集上线后的头 14 天，plugin 也每天跑一遍做对照，结束后停掉。哪种渠道和 web 更一致就用哪种，结果写进变更记录。
- **注意**：runs 表里的 `search_calls` 现在记的是搜索轮数（plugin 15 题共 27 轮），而计费按 `usage.tool_usage.web_search` 算（plugin 共 83 次）。两者要分成两个字段存，成本要按后者算。
- 每日任务：10:00 开始，15 题 × 1 个 API 渠道，串行（并发上限未压测，先不并发）。单次调用失败重试 2 次，仍失败就记为失败的 run，**不补数**。管理员可以在设置页手动触发补跑当天。
- run_id 规则：沿用 schema-v1 的格式，round 用 `daily`，n 用日期：`daily-doubao-api-custom-Q01-20261022`。
- **每题次数**【用户定，2026-10-22：每天一轮、每题 1 次】：设置页加一项「每题次数」（`repeats_per_question`），默认 1，API 和 web 各自一项。设成 k>1 时，同一题当天连问 k 次，第 1 次的 run_id 不变，第 2 次起加后缀 `-r2`、`-r3`。指标口径相应变成「按回答数算」：分母 = 当天 valid 的回答数，自检「同一题当天 valid 不超过 k 条」。改这个值等于改口径，看板趋势图在改动当天画一条竖线并注明。InsGEO 和 AnswerBit 都是每题每轮 2 次、一天多轮，我们不跟，是因为成本和网页采集的风控风险，**不是因为 1 次就够**：每题每天 1 次，看不出同一题的回答本身有多大波动。
- `user_location` 固定为中国 / 广东 / 深圳（schema-v1 已定测量地点为深圳）。注意 api-custom 会忽略这个参数（见下一条）；只有对照期跑 plugin 时才生效。
- 试跑数据（`data/runs/*-trial.csv` 和 `data/raw/trial/`）导入数据库，round 保留为 `trial`，**不进看板主指标**。CSV 里 question_version 记的是 v4，但实际跑的是 v3 的 15 题（两版的 Q01–Q15 完全相同），导入时改成 v3。
- **上线后第一件事是做对照试跑**【我定】：`api-custom` 会忽略 `user_location`，它会不会改用调用方 IP 判断地区，没有核实过。在服务器上跑一轮，和本机的 trial 结果逐题对比信源。差异明显的话，要在看板上注明 api-custom 的地区取决于服务器所在地。
- 每天记录 `search_calls` 和 token 用量，看板上显示当天消耗；单价拿到后在设置里填写，即可显示估算费用。

#### 4.3.1 低频网页采集（`channel=web`）【用户定：要做；细则我定】
- **工具**：在 `worker` 容器（或独立的 `web-collector` 容器）里用 Playwright 跑无头 Chromium，访问豆包网页版。
- **账号**【用户定，2026-10-22：先不登录】：先用**匿名（不登录）**方式采集，`account_ref` 记为 `anonymous`。试验表明匿名可以正常提问、联网和展示信源（见本节末「试验记录」）。公司同时准备手机号注册一个专用账号作为备用，匿名方式被限制时再切换；切换后，账号设置里能关的记忆和个性化选项都关掉，并把设置截图存档。匿名和登录的数据分开标记，不混算。
- **登录（仅备用账号启用后）**：服务器上不做自动登录。由人在本机用浏览器登录一次，导出登录状态（Playwright storage state），在网站的设置页上传。登录状态失效时，当天的网页采集标记为"登录失效"并停止，看板上醒目提示，等人重新上传。
- **每题一个全新浏览器上下文**【我定】：每道题都新建浏览器上下文（不复用 cookie、localStorage），问完即销毁。原因：同一个匿名上下文会在侧栏保留之前的对话，试验中在同一上下文连问 3 题，第 3 题（Q07）的搜索词里出现了题目没提的"澳觅"；换全新上下文重问，搜索词里没有"澳觅"。单次对照，分不清是上下文影响还是回答本身的随机波动，但隔离的成本很低，不论原因都应该这样做。启用登录账号后，每题仍新建上下文，只加载同一份 storage state；账号级的历史和记忆无法靠新建上下文隔离，只能靠关闭记忆选项，这是已知局限。
- **频率和节奏**：每天 1 轮，15 题串行。上一题的回答生成完以后，固定等 2 分钟再问下一题，一轮大约 45 分钟（试验中每题生成耗时 21–30 秒），10:00 和 API 同时开始。间隔是**固定值，不做随机化**：固定间隔是为了减轻负载，随机化就成了规避检测。
- **模式**：用网页版的默认模式，和普通用户一致；界面上显示的模式名称记进 `mode` 字段（试验时匿名默认显示"豆包 快速"）。
- **采集内容**：回答全文、页面上展示的参考资料或信源（标题、链接、站点）、搜索关键词、整页截图、页面 HTML 快照。原始材料一律保留。
  - 信源和搜索关键词默认是折叠的，要先点开"搜索 N 个关键词，参考 M 篇资料"，它们才会出现在 DOM 里（`a[href]`）。采集时必须先展开，再存 HTML。
  - **两个数都记**：页面上写的"参考 M 篇"（`ref_count_claimed`）和实际能看到的链接数（`ref_count_visible`）。两者经常不同（试验：12 篇对 7 条、15 篇对 11 条）。信源指标只用看得到的链接，M 只作参考。
  - **没联网是正常结果**：页面上没有"搜索 N 个关键词"这一块时，记 `web_searched=false`、信源为空，这条 run 算成功，**不算** `parse_failed`。看板上单独统计"未联网"的题数（试验中 Q04 就没联网）。
  - **补抓三样**【用户定，2026-10-22，借鉴 AnswerBit】，都按原样存，不改写：
    - **推荐追问**：回答末尾页面给出的追问（试验中 Q01、Q07 重问各 3 条，例如「澳觅外卖的新用户有哪些优惠活动？」），存成有序列表。用途：看豆包把用户往哪个方向引，可作为扩充题库的候选，**不进指标**。
    - **引用角标**：正文里嵌的来源小标签（试验 Q01 有 3 个：「澳覓APP」「澳覓APP」「澳门本地宝」），存角标文字、链接、在正文中的位置。**角标文字必须从 `answer_text` 里剥掉再做编码**：试验中角标「澳门本地宝」直接拼在了正文「适合游客」后面，角标「澳覓APP」含有澳觅的繁体名，不剥掉的话，题目里没提澳觅的回答也可能被算成"提及澳觅"。这个现象只在 1 题里见到，剥离规则要在 1b 上线前用更多页面验证。
    - **视频信源**：试验中视频没有作为单独卡片出现，而是作为信源列在参考资料里（`iesdouyin.com/share/video/...`，Q07 重问的 11 条信源全是）。信源加一个字段 `content_form`（article / video / app_store / other），按域名和路径规则判断，规则放设置里。用途：§4.7 平台推荐时，能区分"该写文章"还是"该发视频"。
- **解析**：用规则从 DOM 里取回答、关键词和信源，提及和排位照 §4.4 用别名表匹配。试验 3 题中，千问（`qwen3.8-max`）从页面文字抽出的正文、关键词、信源和三家名次与规则结果全部一致，所以 MVP **不引入 LLM 解析**。以后如果用 LLM 给规则解析兜底，它抽出的每条链接必须能在原始 HTML 里原样找到，找不到就丢弃。
- **解析失败**：页面上有回答区域，但解析不出回答，或者显示联网了却解析不出信源，这条 run 标记为 `parse_failed`，原始材料照样保存，**不猜、不补**。网页改版后，解析规则由人来修，修好后可以用保存的原始 HTML 重新解析。
- **停止规则**（触发任何一条，当天剩下的题都不再问，并且不自动重试，要人在设置页点"恢复"才继续）：
  - 页面出现验证码或人机验证
  - 出现风控、频繁操作或账号异常之类的提示
  - 被要求重新登录
  - 连续 3 题失败
- **地区**：网页采集的地区由服务器 IP 决定，所以要记录服务器 IP 的归属地（写进 `location`）。服务器不在深圳的话，网页数据和"测量地点深圳"的口径不一致，看板上要注明。
- **看板**：web 作为单独的渠道展示，绝不和 API 合并。新增一个"**渠道一致性**"视图：每天逐题对比 web 和当前 API 渠道（对照期内再加 api-plugin）三项是否一致——澳觅是否被提及、三家中谁排第一、信源域名的重合度。这样每天都能看到 API 和接近真实用户的数据差多少，原来要专门安排的对照测试就变成了每天自动跑。

### 4.4 编码（判断每条回答提没提到谁、排第几）

#### 4.4.1 品牌归因【用户定，2026-10-22，借鉴 InsGEO 的 attribution】

- **信源归因率** = 提及澳觅、且信源里至少有一条自有 URL（`is_owned`）的回答数 ÷ 提及澳觅的回答数。

- **题目范围 = 全部题，包括带品牌名的**【我定】：§4.5 只排除品牌题的是提及率、首位率、份额这三个数；归因看的是"提到了澳觅以后，能不能让人找到它"，用户直接问"澳觅怎么下载"这类品牌题恰恰最该给出官方入口。页面上写明"全部题中提到澳觅的回答"。
- 匹配规则【我定】：网址和名称不区分大小写；电话只比数字，数字之间允许空格、短横线、括号（"2888 8888"和"28888888"算同一个），国际区号可有可无。

#### 4.6.1 引用周期【用户定，2026-10-22，借鉴 InsGEO；InsGEO 的算法已用它的真实接口数据复算过】
对每篇被引用过的文章（按 `url_norm` 归并），在选定渠道和日期范围内算：
| 字段 | 定义 |
|---|---|
| 被引次数 | 引用过它的 run 数（同一条 run 里出现多次只算 1） |
| 首次 / 末次被引 | 最早 / 最晚的 `collect_date` |
| 活跃天数 | 有被引的不同日期数 |
| 跨度天数 | 末次 − 首次 + 1 |
| 持续度 | 活跃天数 ÷ 跨度天数 |
| 日均被引（能量） | 被引次数 ÷ 活跃天数，即被引的那些天，平均每天被几道题引用（上限 = 当天的回答数） |
| 首次被引耗时 | 首次被引日期 − 发布日期。发布日期：我方文章用回填的发布时间（§4.9）；外部文章用接口返回的 `publish_time`，没有就留空 |

- 不做 InsGEO 的"频率"（被引次数 ÷ 跨度天数）：它等于持续度 × 能量，单独列出没有增加信息。
- **左删失要标出来**：首次被引日期等于该渠道开始采集的第一天时，标"监测开始前可能已被引用"，这种文章的首次被引耗时不计算。不标的话，老文章会被算成"一发布就被引用"。
- 外部文章的 `publish_time` 是接口给的，两种渠道格式不同、可能缺失，也没核实过准不准，页面上注明来源。
- 页面：信源分析加一个「引用周期」表，可以按被引次数、持续度、首次被引耗时排序；GEO 文章的追踪结果（§4.9）用同一套定义。

#### 4.6.2 平台属性【用户定，2026-10-22，借鉴 AnswerBit】
平台映射表每一行加几列：
- **人工填写**：审核宽严（宽 / 中 / 严 / 未知）、能不能带外链、发布注意事项（自由文本）。默认"未知"，由发过文章的人填写。
- **系统实测**：我方在这个平台发的文章，从发布到第一次被引用的天数，显示中位数和样本数，数据来自 §4.9 的发布追踪；样本少于 3 篇时显示"样本不足"，不显示中位数。还没被引用的文章单独计数（"已发 n 篇，未被引 m 篇"），不能直接丢掉，否则中位数会偏小。
- AnswerBit 说的"收录时延"指搜索引擎收录，我们测不到搜索引擎的收录，能测的只是"被豆包引用的时延"，页面上就用这个名字，不叫"收录"。

### 4.8 知识库（RAG）
- 上传 PDF，文字版，单个 100MB 以上【用户定】。上传要支持大文件，建议分片上传加进度条，反向代理放开大小限制。上传之后在后台处理，页面上显示进度。
- 每份文档上传时填写：标题、生效日期、状态（现行 / 失效）。检索时只用现行文档。
- 解析：提取文字层（例如用 PyMuPDF）。整页没有文字的页面，标记为"无文字层，未入库"，并在文档详情页列出来。**不做 OCR**（用户确认是文字版）。
- 风险提示：文字版 PDF 能到 100MB 以上，多半是因为图片多；印在图片里的信息（价目表、海报上的优惠）不会被提取。文档详情页要显示每页提取到的字数，方便发现漏掉的内容。
- 切块：按标题和段落切，保留页码，切块大小和重叠由 builder 定。切块原文、元数据和向量都存 MySQL（见下面 2026-10-23 的决定）。
- **2026-10-23 改回自建，不用 Qdrant**【用户定】：

    - ④ 只检索现行文档：search_knowledge 的 `query_param.doc_filter` 支持按 `doc_id` 过滤（`{"op":"must","field":"doc_id","conds":[...]}`），所以标准版不用标签也能做：检索时传现行文档的 doc_id 列表。文档又说「用于过滤的字段需要在 collection/create 时加到 index_config 的 fields 上」，doc_id 是否也要加，没写清楚，**要实测**；不行就退回「失效即删除」。
    - ⑤ 计费（计费页，2026-09-08）：标准版 0.0416 元/知识库/小时（约 30 元/月），创建后即开始收费；文本向量 0.0005 元/千 tokens；重排 0.0005 元/千 tokens。免费试用条件页面上只有一个「免费体验权益」链接，**未核实**。
    - 处理进度：`/api/knowledge/doc/info` 返回 `status.process_status`（0 成功 / 1 失败 / 2 排队 / 3 更新中 / 5 删除中 / 6 处理中）、`point_num`、`statistics.pages/chars`，失败时有 `failed_code`（如 30001 超过文件大小限制）。
  - 不受影响的部分：§4.11 事实一致性检测用人工维护的事实清单，不依赖知识库；1c 计划也不依赖知识库。
- **检索 = 语义 + 关键词混合**【我定】：
  - 语义向量：用方舟的 embedding 模型生成，**模型 ID = `doubao-embedding-vision-251215`**【用户定，2026-10-21】。注意：这是 vision 模型，支持图文混合，但我们只用文字部分（PDF 是文字版，不做 OCR），成本比纯文本模型高。
  - 关键词：**在应用里用 jieba 分词后自己算 BM25**，和语义结果用 RRF 融合（2026-10-23 起不写 Qdrant）。
  - jieba 要加自定义词典：澳觅、mFood、闪蜂、+86、支付宝、微信支付、澳门通等，不能把它们切碎或过滤掉。
  - 验收：用 10 道左右的真实事实问题（支付方式、内地手机号注册、配送范围等），人工判断检索结果的前 5 条里有没有正确段落。由 builder 和用户一起定一个及格线，达到了才能进入文章生成。
- 知识库做成可替换的接口（上传 / 检索 / 删除），文档元数据（生效日期、现行 / 失效）始终放在 MySQL。以后要换成火山知识库或 Milvus，只改这一层。

### 4.9 GEO 文章
流程：选目标题（可以选多道）+ 目标平台 → 系统给出参照文章 → 用 RAG 检索事实 → 生成初稿 → 人工审核编辑 → 标记为可发布 → 人工发布 → 回填发布链接 → 系统追踪。

- **参照文章**：从这道题的高引用信源里选。系统按 URL 抓取正文，用来学习结构（标题怎么起、开头怎么写、是否有 FAQ 和清单），**不照抄内容**。抓取失败时，允许用户手动粘贴正文。
- **事实挂出处**：生成时要求模型给每条关于澳觅的事实陈述标注 chunk_id。生成完做一次检查：凡是提到澳觅、却没有出处的句子，一律标红，标为"待核实"。
- **审核关卡**：只要还有标红的句子，就不能标记为"可发布"。编辑器里点出处，可以看到 PDF 原文和页码。
- **平台适配**：每个平台一份写作模板（字数、标题风格、格式），可在设置里编辑。初始内容由 builder 拟一版，用户后续调整。
- **发布追踪**：回填链接后，系统把它和此后每天采集到的信源 URL 做规范化匹配（去掉追踪参数，m 站和 www 站视为同一篇）。记录第一次被引用的日期、发布到被引用隔了几天、被哪道题引用。
- 每篇文章记录它覆盖了哪些题（对应 schema-v1 的 content_units）。

### 4.10 App 手测录入
- 表单字段沿用 schema-v1 runs 表（App 渠道必填截图），信源手动逐条录入。
- 手测数据单独一个看板标签页，和 API 数据并排显示，绝不合并计算。
- 手测规则【我定，沿用 schema-v1 §1、§4】：每一轮 15 题全测，每题 3 次，分散在这一轮内的不同日期，所以每轮是 45 次手测。round 记为 `app-YYYYMMDD`（这一轮开始的日期）。指标**按轮聚合**。
- 校准视图：逐题并排显示 App 这一轮的结果，以及同一时间段 API 每日结果的平均值，标出两边差异大的题。

### 4.11 事实一致性检测【用户定，2026-10-22；两家竞品都没做好，是我们的差异点】
豆包回答里关于澳觅的事实说错了没有。试验中已经见到的错误：把澳觅写成"MacauMall"（Q04），把"澳觅 mFood"写成一个 App（Q07 重问）；InsGEO 抽出的澳觅事实也互相矛盾（商户数 5300 / 1600 / 5500 家）。
- **事实清单**（设置页维护）：每条包括事实项（例如"支付方式""能否用内地手机号注册""与 mFood 的关系"）、正确说法、出处（文档名 + 页码，或 URL）、生效日期、状态（现行 / 失效）。**先用人工维护的清单，不依赖知识库**：清单短、可审，第一阶段就能用；知识库上线后，出处可以改成链接到 chunk。初始清单【待用户提供】，我可以先从现有回答里把出现过的澳觅事实列成草稿，由用户逐条确认正误。
- **抽取和判定**：对每条提及澳觅的 valid 回答，用 LLM 抽出"关于澳觅的事实陈述"，每条给出：原句、对应哪个事实项（或"清单里没有"）、判定（一致 / 矛盾 / 无法判断）。模型用方舟，复用 `ARK_API_KEY`，具体模型 ID 由 builder 查官方文档定【我定】。
  - **原句必须能在 `answer_text` 里原样找到**，找不到就丢弃，和 §4.3.1 对 LLM 抽取链接的要求一样。
  - 抽取用的 prompt 和模型 ID 一起记版本号，换了就重新抽。
- **只出待复核列表，不出指标**：判定结果进一个"事实问题"列表，每条能点回原始回答，由人确认"确实错了 / 判错了"。按 §4.4，LLM 做的语义判断，要等和人工判定的 Cohen's κ 达标后才能变成看板上的数字；在那之前，看板上只能显示**人工已确认**的错误条数，并注明是人工确认的。
- 被判"清单里没有"的陈述单独列出：这里面往往有清单该补的事实。
- 用途：确认过的错误事实，对应到 §4.9 写文章时要重点讲清楚的点，也是给官网或知识库补内容的依据。

## 6. 效果衡量的边界
15 题里只有 10 道不带品牌名，每天每题只问 1 次。这种样本下，覆盖题和对照题的双重差分得不出可靠结论。所以 MVP 的"效果"只用一个直接、逐篇可查的指标：**我们发的文章 URL 有没有进入对应题目的信源，从发布到被引用隔了几天。** 它只能证明"文章被豆包收录和引用了"，证明不了提及率的上升是这些文章带来的。页面上要写明这一点。以后扩到 50 题时，数据结构不用改。

## 6.5 实施顺序【我定】
1. **第一阶段：API 采集 + 看板 + 回答记录 + 信源分析 + 优化建议（只到平台推荐）+ 登录 + 部署**。这部分不依赖知识库，做完就上线，每天 10:00 开始积累数据。
   - 1b：低频网页采集 + 渠道一致性视图（含推荐追问、引用角标、视频信源，§4.3.1）。放在 API 采集跑稳以后再做，因为它依赖网页结构，最容易坏，不能拖住第一阶段上线。
   - 1c【2026-10-22 新增】：只用现有数据就能做的三项——每题次数设置项、品牌归因、引用周期，加上平台属性的人工填写列。不依赖网页采集和知识库，可以和 1b 并行。
   - 1d【2026-10-22 新增】：事实一致性检测。依赖用户确认事实清单，清单没到之前只做抽取和"清单里没有"列表。

2. **第二阶段：知识库（自建，向量存 MySQL）+ GEO 文章 + 发布追踪**。知识库先单独做（上传 + 检索 + 验收），GEO 文章另起计划。

这样排的原因：数据越早开始积累，后面的优化建议才有依据；知识库要等用户提供 PDF，还要调检索效果，不确定性最大，不能让它卡住看板上线。
