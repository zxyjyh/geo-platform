# 豆包 GEO 内部网站 设计文档（2026-10-21）

> 上游文档：`docs/schema-v1.md`（数据模型与指标口径，v1.1）、`.claude/tasks/2026-10-20-豆包GEO-T9.md`（交接与历史决策）。本文与 schema-v1 冲突时，以本文为准，并在 schema 升版时同步。
> **本网站和 T-9 验收无关**【用户定，2026-10-21】：不需要支持轮次制基线/复测、50 题、覆盖题/对照题，也不负责出 T-9 的验收报表。
> 标注约定：**【用户定】** = 用户在对话中明确决定；**【我定】** = 设计者的判断，用户可推翻；**【待核实】** = 尚无可靠依据。

## 1. 意图

澳觅（澳门本地生活平台：外卖 / 超市生鲜 / 团购优惠 / 景点门票）想知道：内地游客和本地用户问豆包"澳门点外卖用什么 App"这类问题时，豆包有没有提到澳觅、排第几、引用了哪些网站；再根据这些数据决定去哪些平台发文章、写什么样的文章，并追踪文章有没有被豆包引用。

市面上的 Answerbit（腾讯企点营销云）做的就是这件事，但要收费，所以自建一个只给内部用的版本【用户定】。界面和功能结构参考 Answerbit【用户定】。第一期只做豆包【用户定】。

## 2. 目标 / 非目标 / 反目标

### 目标（MVP）
1. 每天 06:00（北京时间）自动用豆包 API 跑 v3 冻结的 15 道题，**只跑一种联网渠道**【用户定，2026-10-21】，用 `api-custom`（豆包搜索 Custom 版）【用户定，2026-10-21；理由和切换条件见 §4.3】。渠道在设置里可以切换，换了以后看板要按渠道分开显示，不和之前的数据接成一条线。同一天另外用低频网页采集跑一遍这 15 题（`channel=web`），作为"更接近真实用户"的数据【用户定】。
2. 看板显示提及率、首位率、提及份额（澳觅 / mFood / 闪蜂），每个数字可以点进去看到原始回答和信源。
3. 信源分析：按平台统计被引用次数，重点看 7 个可发布平台。
4. 优化建议：找出短板题，结合信源给出"该去哪个平台发"的排序。
5. GEO 文章：基于知识库（RAG）生成文章，每条关于澳觅的事实挂出处，人工审核后手动发布，回填链接，自动追踪这个链接什么时候出现在豆包的信源里。
6. 知识库：上传 PDF（文字版，单个 100MB+）【用户定】，切块入向量库。
7. App 手测录入：每 1–2 周人工在豆包 App 上测一轮，录入后与 API 数据分开展示，用于校准。
8. 部署在公司 Linux 服务器，Docker，公网访问【用户定】，必须登录。

### 反目标（技术上能跑，但出现以下任何一条都算做砸了）
1. **看板上出现不是真实采集得到的数字。** 同事之前用的 WorkBuddy 工作台，提及率是 LLM 按规则模拟出来的，这正是要避免的。任何数字都要能追溯到具体的 run 和原始响应。
2. **API 数据和 App 数据被合并计算，或者被说成是"豆包 App 的表现"。**
3. **包含没有出处的澳觅事实的文章被标记为"可发布"。**
4. **数字不带样本量。** 看板正常展示每日数据【用户定】，但每个比率都要同时显示分子和分母（例如"8/10"），让看的人知道一道题的变化就会带来 10 个百分点的波动。
5. **漏跑的那天用前一天的数顶上。**
6. **为了让指标好看去改口径。** 口径改动只能升 schema 版本。
7. **网页采集为了"跑通"去绕过豆包的防护**，比如破解验证码、伪造指纹、轮换 IP、多账号轮换、随机化行为来躲检测。一旦出现这些做法，性质就从违反用户协议升级为协议 §5.1.2 所说的危害网络安全行为。

### 成功标准【我定，用户未回答，待确认】
上线后一个月内：
- 连续 14 天自动采集成功率 ≥ 13/14；漏跑的天在看板上显示为缺失。
- 每天 07:30 前看板有当天的数据。
- 至少 3 篇文章走完"生成 → 审核 → 发布 → 回填链接"的全流程，系统能自动识别其中任何一篇第一次出现在信源里的日期。
- 不把"提及率提升了多少"当作这个工具的成功标准：15 题、每天 1 次的样本，测不出可靠的因果效果（见 §6）。

## 4. 已决定的"怎么做"

### 4.1 部署架构
- 公司 Linux 服务器，Docker Compose，公网访问【用户定】。
- 容器【我定】：
  - `web`：后端 API + 前端静态文件
  - `worker`：定时任务（每天采集）+ 后台任务（PDF 入库、文章生成）
  - `mysql`：业务数据库【用户定：MySQL】，新起一个容器【我定，若公司要求复用现有实例再改】
  - `qdrant`：向量库【我定，用户授权"听你的建议"】。选它是因为检索时能按元数据过滤（只搜现行版本的文档），MySQL 社区版又算不了向量距离
  - 反向代理（nginx 或 Caddy）负责 HTTPS，并放开大文件上传
- 技术栈【我定】：后端 Python（FastAPI），因为现有采集脚本 `collect/doubao_api.py` 是 Python；前端 React + Ant Design + ECharts。
- 写文章和 embedding 都用火山方舟的模型，复用同一个 `ARK_API_KEY`【我定】。embedding 用哪个模型 ID，**由 builder 查方舟官方文档确定**，不要凭记忆写。

### 4.2 安全
- 必须登录，没有公开页面。账号由管理员创建，所有人权限相同【我定】。密码哈希存储，登录接口限流。
- `ARK_API_KEY` 只放服务器上的环境变量或 `.env`，不进数据库、不进代码仓库、不在页面上显示。之前在对话里出现过的 Key 要在上线前轮换。
- 公网暴露的风险：需要用户提供域名和 HTTPS 证书方案【待用户提供】。
- **服务器在内地，公司有域名**【用户定】：用这个域名下的一个子域名（例如 `geo.<公司域名>`）。上线前要请运维确认两件事：这个域名已经做过 ICP 备案；备案的接入商和服务器所在的云厂商是同一家。如果不是同一家，要先做「新增接入」。

### 4.3 数据来源与采集
- 复用 `collect/doubao_api.py` 里的 `build_body` / `parse_response` / `search_queries`，改成写 MySQL（原始响应 JSON 照旧落盘或存库）。
- **渠道选择**【用户定，2026-10-21；我推荐时的把握约 55%】：用 `api-custom`。依据是 trial 数据（每题只跑了 1 次）：
  - 两种渠道的信源域名重合度很低：逐题 Jaccard 平均 0.23，有 3 道题完全没有重合，说明它们背后是两套不同的搜索；
  - 原始响应的 `usage.tool_usage_details` 里，custom 标为 `doubao`，plugin 标为 `search_engine`，所以推测 custom 用的是豆包自己的搜索，更可能接近豆包产品，**这一点没有核实**；
  - 计费的搜索次数，custom 是 42 次/15 题，plugin 是 83 次/15 题；
  - 代价：custom 会忽略 `user_location`，每次返回的信源也少一些（平均 4.6 条，plugin 是 6.4 条）。
  - **切换条件**：网页采集（§4.3.1）攒满 14 天后，比较两种渠道和 web 在"是否提及澳觅"上的逐题一致率。为此，网页采集上线后的头 14 天，plugin 也每天跑一遍做对照，结束后停掉。哪种渠道和 web 更一致就用哪种，结果写进变更记录。
- **注意**：runs 表里的 `search_calls` 现在记的是搜索轮数（plugin 15 题共 27 轮），而计费按 `usage.tool_usage.web_search` 算（plugin 共 83 次）。两者要分成两个字段存，成本要按后者算。
- 每日任务：06:00 开始，15 题 × 1 个 API 渠道，串行（并发上限未压测，先不并发）。单次调用失败重试 2 次，仍失败就记为失败的 run，**不补数**。管理员可以在设置页手动触发补跑当天。
- run_id 规则：沿用 schema-v1 的格式，round 用 `daily`，n 用日期：`daily-doubao-api-custom-Q01-20261022`。
- `user_location` 固定为中国 / 广东 / 深圳（schema-v1 已定测量地点为深圳）。注意 api-custom 会忽略这个参数（见下一条）；只有对照期跑 plugin 时才生效。
- 试跑数据（`data/runs/*-trial.csv` 和 `data/raw/trial/`）导入数据库，round 保留为 `trial`，**不进看板主指标**。CSV 里 question_version 记的是 v4，但实际跑的是 v3 的 15 题（两版的 Q01–Q15 完全相同），导入时改成 v3。
- **上线后第一件事是做对照试跑**【我定】：`api-custom` 会忽略 `user_location`，它会不会改用调用方 IP 判断地区，没有核实过。在服务器上跑一轮，和本机的 trial 结果逐题对比信源。差异明显的话，要在看板上注明 api-custom 的地区取决于服务器所在地。
- 每天记录 `search_calls` 和 token 用量，看板上显示当天消耗；单价拿到后在设置里填写，即可显示估算费用。

#### 4.3.1 低频网页采集（`channel=web`）【用户定：要做；细则我定】
- **工具**：在 `worker` 容器（或独立的 `web-collector` 容器）里用 Playwright 跑无头 Chromium，访问豆包网页版。
- **账号**：一个公司专用账号，只用于采集，`account_ref` 记录这个账号的代号。账号设置里能关的记忆和个性化选项都关掉，并把设置截图存档。
- **登录**：服务器上不做自动登录。由人在本机用浏览器登录一次，导出登录状态（Playwright storage state），在网站的设置页上传。登录状态失效时，当天的网页采集标记为"登录失效"并停止，看板上醒目提示，等人重新上传。
- **频率和节奏**：每天 1 轮，15 题串行，每题都新开对话。上一题的回答生成完以后，固定等 2 分钟再问下一题，一轮大约 45 分钟，06:00 和 API 同时开始。间隔是**固定值，不做随机化**：固定间隔是为了减轻负载，随机化就成了规避检测。
- **模式**：用网页版的默认模式，和普通用户一致；如果界面上能看到模式名称，记进 `mode` 字段。
- **采集内容**：回答全文、页面上展示的参考资料或信源（标题、链接、站点）、整页截图、页面 HTML 快照。原始材料一律保留。
- **解析失败**：解析不出回答或信源时，这条 run 标记为 `parse_failed`，原始材料照样保存，**不猜、不补**。网页改版后，解析规则由人来修，修好后可以用保存的原始 HTML 重新解析。
- **停止规则**（触发任何一条，当天剩下的题都不再问，并且不自动重试，要人在设置页点"恢复"才继续）：
  - 页面出现验证码或人机验证
  - 出现风控、频繁操作或账号异常之类的提示
  - 被要求重新登录
  - 连续 3 题失败
- **地区**：网页采集的地区由服务器 IP 决定，所以要记录服务器 IP 的归属地（写进 `location`）。服务器不在深圳的话，网页数据和"测量地点深圳"的口径不一致，看板上要注明。
- **看板**：web 作为单独的渠道展示，绝不和 API 合并。新增一个"**渠道一致性**"视图：每天逐题对比 web 和当前 API 渠道（对照期内再加 api-plugin）三项是否一致——澳觅是否被提及、三家中谁排第一、信源域名的重合度。这样每天都能看到 API 和接近真实用户的数据差多少，原来要专门安排的对照测试就变成了每天自动跑。

### 4.4 编码（判断每条回答提没提到谁、排第几）
- **提及（mention）和排位（order）用别名表做字符串匹配**，规则见 schema-v1 §2.4、§2.6【我定】。原因：结果确定、可复现，不依赖 LLM。别名表要带版本号，别名表一改，全部重算。
- **只考虑澳觅、mFood、闪蜂三家**【用户定，2026-10-21】：排位只在这三家之间比较，看首次出现的先后顺序。这和 schema-v1 §2.4 写的"所有平台"口径不一样，schema 要相应升版。指标在页面上命名为"**三家中首位率**"，不能写成"首位率"。原因是：如果 Klook 排在最前面、澳觅第二，澳觅在这个口径下仍然算第一，名字不写清楚就会被误读。
- 推荐（recommend）、情感（sentiment）、事实错误需要语义判断，**MVP 不上看板**。等以后用 LLM 编码，并且和人工编码的 Cohen's κ 达到 schema-v1 §3.3 的门槛后再加。
- 已知局限：字符串匹配会把"不建议用澳觅"也算成提及，这符合 schema 对 mention 的定义（mention 只看有没有出现），不算 bug。

### 4.5 指标
- 看板**正常展示每日数据，不做 7 天窗口**【用户定，2026-10-21】。主数字是最近一次采集那天的值，下面放每日趋势图，可以选日期范围查看历史。
- 提及率、首位率、提及份额只算 10 道不带品牌名的题（v3 里 Q03、Q12–Q15 带品牌名，排除在外）。
- 每个比率同时显示分子和分母，例如"提及率 8/10"【我定】。区间和 bootstrap 这期不做。
- 当天有题采集失败时，分母就是实际成功的题数，并标出缺了哪几题。
- 提及份额 = 当天澳觅被提及的次数 ÷ 三家被提及次数之和（schema-v1 §3 的定义）。
- 各渠道（API / web / App 手测）分开显示，不加总。
- 出数前自动跑 schema-v1 §3.1 中适用的自检（如：三家中首位率 ≤ 提及率；不混渠道）。任何一条不通过，该指标显示"自检未通过"和原因，不出数字。

### 4.6 信源与平台
- 平台映射表（可在设置里编辑）【我定，初始值】：什么值得买 `smzdm.com`、头条号 `toutiao.com`、百家号 `baijiahao.baidu.com`、搜狐 `sohu.com`、B站 `bilibili.com`、网易号 `163.com`、知乎 `zhihu.com`。按主域名匹配，子域名也算（`m.sohu.com`、`post.m.smzdm.com`）。
- 信源可以人工打标签"外部 GEO 文章"（比如那批搜狐文章），这类信源单独统计。
- 信源类型（source_type）和是否自有（is_owned）沿用 schema-v1 §2.3；自有渠道清单在设置里维护，目前用户还没提供。

### 4.7 优化建议
- 短板题的定义【我定，可在设置里调】：不带品牌名的题，最近 7 次采集里满足以下任一条件：澳觅被提及的次数不到一半；mFood 或闪蜂排在澳觅前面的次数多于澳觅排第一的次数。这里看 7 次，是为了让建议不被某一天的偶然结果带偏，和看板的展示方式无关。
- 对每道短板题，统计近 30 天它的信源里 7 个平台各被引用多少次，据此给出平台推荐排序。引用次数为 0 的平台照样列出，但标"未验证"【用户认可的方向】。
- 同时列出这道题被引用最多的几篇文章，作为写作参照。
- 平台推荐按渠道分别统计。web 数据攒满 7 天后，默认按 web 的信源来排（它最接近真实用户）【我定】，同时能切换到 API 查看。页面上固定写明数据来自哪个渠道。

### 4.8 知识库（RAG）
- 上传 PDF，文字版，单个 100MB 以上【用户定】。上传要支持大文件，建议分片上传加进度条，反向代理放开大小限制。上传之后在后台处理，页面上显示进度。
- 每份文档上传时填写：标题、生效日期、状态（现行 / 失效）。检索时只用现行文档。
- 解析：提取文字层（例如用 PyMuPDF）。整页没有文字的页面，标记为"无文字层，未入库"，并在文档详情页列出来。**不做 OCR**（用户确认是文字版）。
- 风险提示：文字版 PDF 能到 100MB 以上，多半是因为图片多；印在图片里的信息（价目表、海报上的优惠）不会被提取。文档详情页要显示每页提取到的字数，方便发现漏掉的内容。
- 切块：按标题和段落切，保留页码，切块大小和重叠由 builder 定。切块原文和元数据存 MySQL，向量存 Qdrant，两边用 chunk_id 关联。
- **向量库用自建 Qdrant**【用户定，2026-10-21】。备选方案（火山知识库标准版、Milvus）的对比见下面「知识库选型记录」。
- **检索 = 语义 + 关键词混合**【我定】：
  - 语义向量：用方舟的 embedding 模型生成，**模型 ID = `doubao-embedding-vision-251215`**【用户定，2026-10-21】。注意：这是 vision 模型，支持图文混合，但我们只用文字部分（PDF 是文字版，不做 OCR），成本比纯文本模型高。
  - 关键词：**在应用里用 jieba 分词后自己算 BM25 稀疏向量**，写入 Qdrant 的 sparse vector，查询时用 Qdrant 的 hybrid query（`prefetch` + RRF 融合）。
  - 为什么不用 Qdrant 内置的 BM25：它的官方示例走的是 Qdrant Cloud 推理，开源 Docker 版能不能用，文档没写清楚；`multilingual` 分词器也没有点名中文。这一点没有核实，所以不依赖它。
  - jieba 要加自定义词典：澳觅、mFood、闪蜂、+86、支付宝、微信支付、澳门通等，不能把它们切碎或过滤掉。
  - 验收：用 10 道左右的真实事实问题（支付方式、内地手机号注册、配送范围等），人工判断检索结果的前 5 条里有没有正确段落。由 builder 和用户一起定一个及格线，达到了才能进入文章生成。
- 知识库做成可替换的接口（上传 / 检索 / 删除），文档元数据（生效日期、现行 / 失效）始终放在 MySQL。以后要换成火山知识库或 Milvus，只改这一层。

#### 知识库选型记录（2026-10-21，均读自官方文档）
| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 火山知识库标准版 | 免开发解析和切块；有图片 OCR 开关；约 30 元/月 | 每天只能检索 300 次，最多 500 份文档，不支持标签；页码"可能"返回；文档存在第三方 | 备选 |
| Milvus（v3.0.3） | 内置 `chinese` 分词器（jieba）+ BM25 + 混合检索 | 要 3 个容器（etcd/MinIO/standalone），内存最低 8G、推荐 16G；内置 `chinese` 分词器的 `cnalphanumonly` 过滤器会丢掉 mFood、+86 这类词 | 备选 |
| Qdrant | 1 个容器，轻量 | 中文 BM25 要自己算 | **采用** |

### 4.9 GEO 文章
流程：选目标题（可以选多道）+ 目标平台 → 系统给出参照文章 → 用 RAG 检索事实 → 生成初稿 → 人工审核编辑 → 标记为可发布 → 人工发布 → 回填发布链接 → 系统追踪。

- **参照文章**：从这道题的高引用信源里选。系统按 URL 抓取正文，用来学习结构（标题怎么起、开头怎么写、是否有 FAQ 和清单），**不照抄内容**。抓取失败时，允许用户手动粘贴正文。
- **事实挂出处**：生成时要求模型给每条关于澳觅的事实陈述标注 chunk_id。生成完做一次检查：凡是提到澳觅、却没有出处的句子，一律标红，标为"待核实"。
- **审核关卡**：只要还有标红的句子，就不能标记为"可发布"。编辑器里点出处，可以看到 PDF 原文和页码。
- **平台适配**：每个平台一份写作模板（字数、标题风格、格式），可在设置里编辑。初始内容由 builder 拟一版，用户后续调整。
- **发布追踪**：回填链接后，系统把它和此后每天采集到的信源 URL 做规范化匹配（去掉追踪参数，m 站和 www 站视为同一篇）。记录第一次被引用的日期、发布到被引用隔了几天、被哪道题引用。
- 每篇文章记录它覆盖了哪些题（对应 schema-v1 的 content_units）。

### 4.10 App 手测录入
- 表单字段沿用 schema-v1 runs 表（App 渠道必填截图），信源手动逐条录入。
- 手测数据单独一个看板标签页，和 API 数据并排显示，绝不合并计算。
- 手测规则【我定，沿用 schema-v1 §1、§4】：每一轮 15 题全测，每题 3 次，分散在这一轮内的不同日期，所以每轮是 45 次手测。round 记为 `app-YYYYMMDD`（这一轮开始的日期）。指标**按轮聚合**。
- 校准视图：逐题并排显示 App 这一轮的结果，以及同一时间段 API 每日结果的平均值，标出两边差异大的题。

## 6. 效果衡量的边界
15 题里只有 10 道不带品牌名，每天每题只问 1 次。这种样本下，覆盖题和对照题的双重差分得不出可靠结论。所以 MVP 的"效果"只用一个直接、逐篇可查的指标：**我们发的文章 URL 有没有进入对应题目的信源，从发布到被引用隔了几天。** 它只能证明"文章被豆包收录和引用了"，证明不了提及率的上升是这些文章带来的。页面上要写明这一点。以后扩到 50 题时，数据结构不用改。

## 6.5 实施顺序【我定】
1. **第一阶段：API 采集 + 看板 + 回答记录 + 信源分析 + 优化建议（只到平台推荐）+ 登录 + 部署**。这部分不依赖知识库，做完就上线，每天 06:00 开始积累数据。
   - 1b：低频网页采集 + 渠道一致性视图。放在 API 采集跑稳以后再做，因为它依赖网页结构，最容易坏，不能拖住第一阶段上线。
2. **第二阶段：知识库（Qdrant）+ GEO 文章 + 发布追踪**。
3. **第三阶段：App 手测录入 + 校准视图**。

这样排的原因：数据越早开始积累，后面的优化建议才有依据；知识库要等用户提供 PDF，还要调检索效果，不确定性最大，不能让它卡住看板上线。
