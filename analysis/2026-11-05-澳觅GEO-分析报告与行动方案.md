### 2.3 豆包到底引用什么（174 条信源）——这是「去哪发文章」的直接依据

**可发布平台中被真实引用的只有 3 个：**

| 平台 | 被引次数 |
|---|---|
| 搜狐 | 17 |
| 什么值得买 | 12 |
| 头条号 | 7 |
| 百家号 / B站 / 网易号 / 知乎 | **0** |
| **小红书** | **0**（甚至不在 platforms 监测表里） |

未提交改动把平台从 7 砍到 3，与数据完全吻合。

**高频域名聚类（前几名）：**
- apps.apple.com ×23 —— **App Store 页面是豆包最大单一信源**。App 商店的应用描述、版本更新文案本身就是 GEO 阵地，成本几乎为零
- 澳门政府/旅游局域名合计 ×26（macaotourism.gov.mo 7、gov.mo 6、dsat 4、gcs 3、dst 3 等）—— 权威来源偏好明显；能上政府/旅游局推荐名录、授权名单的价值大于发十篇软文
- smzdm ×12、sohu ×15、toutiao ×7 —— 内容平台的实际盘子
- klook.cn ×5、bento.travel、cloudpipeme 等旅游垂类 —— 游客场景（Q06/Q07/Q09）的引用主力，对应短板题
- aomi.mo（官网）仅 ×3 —— **自有官网被引用太少**，官网内容结构（FAQ、数据页）值得按 citation 友好方式重做

### 2.4 关于「发小红书」的数据判断

当前 3 天数据里，豆包 web_search（api-custom 渠道）**没有引用过任何小红书链接**。这不等于小红书无价值，但意味着：
- 「发小红书 → 被豆包引用」这条路**在本项目现有数据里没有证据**
- 小红书的价值假设需要重新锚定：是对其他 AI 平台（元宝/Kimi 是否引小红书，未验证）、还是对小红书站内搜索本身
- 优先级应低于：搜狐/什么值得买/头条号（已证实被引）、App Store 描述、官网改造

### 2.5 事实一致性问题（历史试验发现，管道未跑通）

- Q04 回答曾把澳觅写成「MacauMall」；Q07 曾把「澳觅」「mFood」当成一个 App（品牌混淆）；Q06 出现过「澳覓（mFood）」写法
- fact_items 已人工确认 7 条正确事实（合作商户 5,700+、App 版本 5.10.1、注册用户 300 万+、2016-06-01 上线等）
- 但 fact_claims=0：自动抽取没跑通（T8 超时），**「豆包说错了什么」目前只能靠人眼**。修复路径 = 先修 T8，再把确认的错误事实喂给文章管道（spec §4.11 已设计好这个衔接）

## 三、三大后期方向：可行性与路线

（本节含外部调研，待补：多平台 API 官方文档核实、内容平台自动发布条款核实）

### 3.1 接入其他 AI 平台的 GEO 监测

**代码侧改造量评估（已核源码）：**
- `models.Run.platform` 字段已存在（默认 "doubao"），全链路（analysis/metrics/api/web）都带 platform 参数透传——**数据模型不用动**
- 耦合点在三处：① `app/ark.py` 是方舟专用客户端；② `app/collector.py:43` run_id 硬编码 `daily-doubao-...`、`:82` platform="doubao"；③ worker.py 只实例化 ArkClient
- 结论：接一个新平台 = 写一个该平台的 client（对齐 ArkResult 接口：text + sources + search_queries）+ collector 参数化 platform + 各平台信源解析适配。**架构上预留是对的，改造是「加适配器」级别，不是重构**
- 竞品一手证据（.spike/insgeo/dump1.clean.json）：InsGEO 的「元宝」数据实为 deepseek+hunyuan API 模拟（think_content 泄露），并非元宝 App——**「8 平台监测」有水分，别把它当标杆**

**各平台接入途径（待外部调研补充官方文档结论）：**
- 元宝 / Kimi / DeepSeek / 通义 / 文心：API 有无、是否返回联网搜索引用 URL（GEO 监测的硬需求）、定价、门槛——见调研报告附表

**关键判断：** 多平台的价值排序应由「该平台是否真的返回引用来源 URL」决定。拿不到引用 URL 的平台只能测提及率，价值减半。

### 3.2 根据反馈数据自动生成文章 + 图片

**这是三个方向里基础最好的一个——spec §4.9 已把管道设计完整，只欠实现：**

```
短板题(已有:weak_questions) → 参照文章(已有:reference_articles)
→ RAG检索事实(已有:kb 215 chunks + fact_items 7条)
→ 生成初稿(未实现) → 每句澳觅事实挂chunk出处、无出处标红(未实现)
→ 人工审核(未实现,反目标3:有标红不许标可发布)
→ 人工发布 → 回填链接(未实现) → 引用追踪(已有:citation_lifecycle + urls.normalize_url)
```

- 数据反馈侧全部就绪：短板题识别、参照文章榜、事实清单、引用周期追踪都在
- 缺口只有中间「生成 + 审核 + 回填」一段，且 T8（事实抽取）修好后，「豆包说错的事实」会自动成为选题输入
- **图片生成**是 spec 没有的新增需求：可接方舟系（即梦/Seedream）或百炼（通义万相）文生图 API，产出封面图/插图。建议第一版做成「生成候选图 + 人工挑选」，不进全自动
- 反目标红线依然有效：**没有出处的澳觅事实不许标「可发布」**——自动化程度再高，这道人工审核关卡不能拆

### 3.3 自动发布到各平台（含小红书）

（待外部调研补充：各平台官方发文 API 有无、申请门槛、自动化条款、封号风险）

**先给灰度框架（不二元）：**
- **档 1（半自动，spec 原设计）**：系统生成好文章+图片 → 人工复制粘贴到各平台 → 回填链接。零合规风险，Answerbit 也是这么做的（spec 非目标原文：「自动发布到各平台：发布靠人工复制粘贴」）。每篇多花 5-10 分钟
- **档 2（官方 API 直发）**：仅限有官方发文 API 且我们满足申请条件的平台（待调研确认哪些平台存在这条路）
- **档 3（浏览器自动化野路子）**：技术上可行但违反多数平台服务条款，封号风险 + 品牌账号资产损失。**小红书点名场景大概率落在这一档**（待调研确认），若走此档必须：专用账号隔离、公司层面书面接受风险（同 10-21 网页采集的决定流程）、出现风控信号即停
- 注意：现在要做的「自动发布」正是 spec 里用户自己批准的非目标。推翻它没问题，但应像当时对待网页采集一样：把条款和风险告知 → 公司决定接受 → 记录进 spec

## 四、分期交付计划（2026-11-05 第二轮补充：产物 / 完成标准 / 卡点风险）

分期原则：按依赖链排，不按功能清单排；每期完成标准写成可跑的验收命令；
「需外部输入」= 用户/公司要提供的东西，它们才是真正的工期卡点（纯开发是本项目已被证明最快的部分：3 天 69 commits）。
时间估算按「1 名开发 + AI 协作」模式给区间，人力变量一变区间就变。

### 第零期：止血与上线（建议 3-5 个工作日，不含公司流程耗时）

**交付产物：**
1. 线上可登录的正式站点（公网域名 + RDS），每日 10:00 自动采集恢复
2. 全绿测试的干净 git 工作区（6 个未提交文件收口）
3. 事实问题列表开始出真实数据（T8 修复后 fact_claims 非空）
4. 看板显示采集断档期（10-25～恢复日）为缺失，不用旧数顶（反目标 5）

**完成标准（可机械验收）：**
- `sqlite3 data/geo.db "SELECT max(collect_date) FROM runs"` 连续 3 天前进；job_runs 每天新增 done 行
- `.venv/bin/python -m pytest -q` → 0 failed
- `git status` 干净；RDS 上 `alembic current` = head
- 生产站点每天 11:30 前有当天数据（spec 成功标准原文）
- `SELECT count(*) FROM fact_claims` > 0，且抽 3 条人工核对「原句能在 answer_text 原样找到」

**需外部输入：** 子域名 + ICP 备案确认、RDS 执行权限、ARK_API_KEY 轮换（旧 key 在对话中暴露过）、火山控制台联网搜索单价（填进 settings 的空字段）

**卡点与风险：**
| 风险 | 触发信号 | 预案 | 止损线 |
|---|---|---|---|
| 备案/域名流程耗时不可控（公司流程） | 一周内没批下来 | 备案与数据解耦：先在内网/本机重启 worker 积累数据，域名好了再切 | 不设——备案多久都要先把采集跑起来 |
| RDS 迁移翻车 | alembic upgrade 报错 | task 文件记载已在 MySQL 8.0.36 容器验证过升/降/带数据升级；执行前 mysqldump 备份 | 迁移失败即回滚 SQLite，不硬修 |
| 采集恢复后失败率高 | status=failed 占比 >20% 连续 3 天 | 查 ARK key/模型版本/计费；已有 failed 删掉重跑机制（collector 自带） | 连续 3 天失败停采排查，不烧钱重试 |
| 豆包快照模型更新导致口径漂移 | 提及率突变、回答文风变化 | DEFAULT_MODEL 已固定快照版（doubao-seed-2-1-pro-260915）；升级模型必须在看板画竖线、分开展示 | 不为指标好看偷偷换模型（反目标 6） |

### 第一期：内容管道——「反馈数据 → 文章 + 图片 → 发布 → 被引用追踪」（建议 2-3 周）

**为什么它排在多平台监测前面：** 监测更多平台而不生产内容，只会看到更多输的地方。
GEO 的终极动作是「让 AI 引用我们的内容」，spec §4.9 已把管道设计完整、kb/短板题/参照文章/引用追踪四个环节的代码已存在，缺口只有中间的「生成+审核+回填」一段。（对调条件：如果业务上更急需给领导看多平台报表，第一/二期可对调，前提是第二期预算已批。）

**交付产物：**
1. 「GEO 文章」页面：文章列表（草稿/审核中/可发布/已发布/已被引用五状态）+ 审核编辑器（标红句、点出处看 PDF 原文页码）
2. 生成器：选短板题 + 目标平台 → RAG 检索事实 → 初稿，每句澳觅事实带 chunk_id 出处，无出处自动标红
3. 图片生成：每篇 3 张候选封面/插图，人工选 1（不进全自动）
4. 发布回填 + 引用追踪：回填链接后自动与每日信源做规范化 URL 匹配，记录首次被引日期
5. 首批真实产出：**3 篇文章走完全流程**（选题直接按数据：Q07 游客必备 APP > Q12 对比 mFood > Q08 支付方式；平台按被引证实：搜狐/什么值得买/头条号）
6. 两件零成本副产品：App Store 应用描述改写稿（apps.apple.com 被引 23 次是最大单一信源）、官网 FAQ/数据页改造清单（aomi.mo 仅被引 3 次）

**完成标准：**
- 3 篇文章状态机各走到「已发布」，其中任意一篇被引用时系统自动记录首引日期（spec 成功标准原文：「至少 3 篇文章走完生成→审核→发布→回填链接的全流程」）
- 反目标 3 程序化强制：存在标红句时「标记可发布」按钮后端直接拒绝（有 API 测试）
- 事实错误输入打通：factcheck 确认过的错误出现在对应文章的「必须讲清楚的点」里

**需外部输入：** **发布账号**——搜狐号/什么值得买/头条号账号有没有、在谁手里、谁能发（没有账号这一期发不出去）；平台写作模板初稿确认；图片生成 API 选型（方舟即梦/百炼万相，需对应 key 与预算）

**卡点与风险：**
| 风险 | 触发信号 | 预案 | 止损线 |
|---|---|---|---|

### 第二期：多平台 GEO 监测接入（每平台 1-2 周，首个平台含采集层改造）

**交付产物：**

2. 新接入平台的每日数据进看板：提及率/排位/信源按平台分列，绝不与豆包合并（反目标 2）
3. 跨平台一致性指标（Kendall W）激活（竞品分析时标记「只做豆包暂不需要」，多平台后需要）
4. 每平台一页「接入判定」：官方 API 有无 / 是否返回引用 URL / 单价 / 门槛——**只接「有官方 API 且返回引用 URL」的平台**；拿不到引用 URL 的平台只能测提及率，价值减半，单独决策

**月成本实算（基于真实 token 用量，非拍脑袋）：**
豆包 31 条 valid run 实测：平均输入 15,482 tok/次、输出 943 tok/次（联网搜索把输入撑大）。按 15 题 × 30 天 = 450 次/月 ≈ 输入 6.97M + 输出 0.42M tok/月，套用调研拿到的官方单价（假设其他平台 token 用量与豆包同量级，±50% 浮动不影响结论）：
- 通义 qwen3.7-plus（2/8 元每 M tok，限时 8 折）≈ **17 元/月**
- TokenHub Hy3（1/4 元）≈ 9 元/月（仅作元宝系近似时）
- DeepSeek flash 忙时（2/8 元）≈ 17 元/月 + 搜索 2.25 元
- 文心 ERNIE 5.1（4/18 元）≈ 36 元/月；或百度AI助手按次 0.056 元 × 450 ≈ 25 元/月
- Kimi k2.6（6.5/27 元）≈ 57 元/月 + 搜索 4.5 元
**结论：单平台 10-60 元/月，五平台全接 ≤250 元/月——预算不是第二期的卡点，开发适配工作量和「有无引用 URL」才是。**

**完成标准：**
- 新平台连续 7 天自动采集成功率 ≥6/7，看板按平台分列展示

- 抽检 3 条新平台回答：引用 URL 能在原始响应 json 里找到（raw_path 落盘可溯）

**需外部输入：** 目标平台 API 开户（实名/企业认证流程与耗时因平台而异）、每平台月预算上限、接入优先级排序（业务定：先测哪个平台对决策最有用）
